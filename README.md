# happy-edu

Заготовка сайта: Node.js (Express) + PostgreSQL + Vue 3 (Vuetify), всё в Docker.
Работает на https://smartalise.ru.

Как включиться в разработку — [CONTRIBUTING.md](CONTRIBUTING.md).

## Авторизация

E-mail + пароль, сессия в httpOnly cookie.

**Самостоятельной регистрации нет** — учётные записи заводит администратор
(см. «Заведение пользователей администратором»), первого администратора создаёт
CLI-скрипт. Эндпоинт `/api/auth/register` удалён из кода целиком, а не закрыт
настройкой: то, чего нет, нельзя случайно включить обратно.

| Метод | Эндпоинт           | Назначение                    |
| ----- | ------------------ | ----------------------------- |
| POST  | `/api/auth/login`  | вход                          |
| POST  | `/api/auth/logout` | выход, сбрасывает cookie      |
| GET   | `/api/auth/me`     | текущий пользователь либо 401 |

## Роли и права

Три роли, заданные в `backend/src/roles.js` — единственном месте, откуда их берут
и схема БД, и проверки доступа:

| Роль      | Права                                                      |
| --------- | ---------------------------------------------------------- |
| `user`    | нет (роль по умолчанию у заведённых пользователей)         |
| `student` | нет — ученик видит своё по принадлежности данных, см. ниже |
| `admin`   | все права из `PERMISSIONS` — максимальный набор            |

Администратор получает все права из `PERMISSIONS`, включая те, что появятся
позже: новое право достаточно добавить в этот объект.

Сейчас их пять: `users:read`, `users:write`, `roles:manage`, `content:write`,
`settings:manage`.

**Доступ решается двумя разными механизмами, и смешивать их не нужно.** Для
персонала — права из таблицы ниже. Для кабинета ученика (`/api/me/*`) — сама
принадлежность данных: у роли `student` прав нет вообще, зато каждый запрос
находит профиль вошедшего и чужого не отдаёт, а не-ученик получает 404.

| Метод  | Эндпоинт                            | Требуемое право                                  |
| ------ | ----------------------------------- | ------------------------------------------------ |
| GET    | `/api/admin/roles`                  | `users:read`                                     |
| GET    | `/api/admin/users`                  | `users:read`                                     |
| POST   | `/api/admin/users`                  | `users:write` (+ `roles:manage` на роль `admin`) |
| PATCH  | `/api/admin/users/:id/role`         | `roles:manage`                                   |
| DELETE | `/api/admin/users/:id`              | `users:write`                                    |
| \*     | `/api/admin/students/*`, `/plans/*` | `users:read` на чтение, `users:write` на правку  |
| \*     | `/api/catalog/*` (правка)           | `content:write`                                  |
| GET    | `/api/admin/settings/gamification`  | `users:read`                                     |
| PUT    | `/api/admin/settings/gamification`  | `settings:manage`                                |
| GET    | `/api/admin/analytics/*`            | `users:read`                                     |

### Заведение пользователей администратором

Единственный способ появиться новому пользователю — администратор заводит его
сам: кнопка «Добавить» в панели пользователей. Пароль можно
задать вручную или оставить поле пустым: тогда сервер сгенерирует случайный
и покажет его **один раз** (в базе хранится только хеш, повторно показать
его неоткуда).

Создание пользователя с ролью `admin` требует отдельного права `roles:manage`:
`users:write` позволяет завести обычного пользователя, но не выдать
администраторские права.

Принятые решения:

- **Роль не кладётся в JWT**, а читается из БД на каждом запросе — иначе снятие
  прав начало бы действовать только после истечения токена (до 7 дней).
- **Публичной регистрации нет**: учётные записи заводит администратор, поэтому
  посторонний не может даже создать себе аккаунт без прав.
- **Нельзя сменить собственную роль** — администратор случайно закрыл бы себе доступ.
- **Нельзя снять права с последнего администратора** (409): проверка идёт в
  транзакции с `FOR UPDATE` на строках админов, что защищает и от одновременного
  взаимного понижения двумя администраторами.
- **Права отдаются фронтенду развёрнутым списком** в `/api/auth/me`, поэтому
  интерфейсу не нужно знать таблицу ролей. Это только для отображения — доступ
  всё равно решает сервер.

### Создание администратора

Первый администратор заводится из командной строки — через сайт войти пока
некому:

```bash
# на сервере, из директории проекта
docker compose -f docker-compose.prod.yml -p happy-edu exec backend \
  node src/create-admin.js admin@example.com

# локально
docker compose exec backend node src/create-admin.js admin@example.com
```

Без пароля в аргументах он генерируется и печатается один раз. Пароль можно
задать явно — аргументом или переменной `ADMIN_PASSWORD` (она не попадает
в историю оболочки):

```bash
docker compose exec -e ADMIN_PASSWORD='...' backend node src/create-admin.js admin@example.com
```

Скрипт идемпотентен: если пользователь уже существует, он повышается до
администратора, а пароль меняется только когда передан явно. Дальше роли
раздаются через админ-панель на сайте, и командная строка больше не нужна:
там же заводятся новые пользователи.

Принятые решения:

- **Пароли** хешируются встроенным в Node `crypto.scrypt` (N=32768, r=8, p=1),
  соль на пользователя, сравнение через `timingSafeEqual`. `bcrypt` не взят
  намеренно: требует нативной сборки в alpine.
- **Сессия** — JWT на 7 дней в cookie `session` с `httpOnly`, `sameSite=lax`
  и `Secure` в проде (флаг `COOKIE_SECURE`, локально выключен, иначе браузер
  не сохранит cookie на http://localhost).
- **E-mail нормализуется** в нижний регистр, уникальность обеспечена индексом
  `users_email_lower_idx` по `lower(email)`.
- **Неверный пароль и несуществующий пользователь** дают одинаковый ответ 401,
  чтобы перебором нельзя было выяснить зарегистрированные адреса.
- **Схема БД** описана миграциями в `backend/migrations/*.sql`, они применяются
  при старте backend (см. раздел «Миграции»).

`JWT_SECRET` обязателен — без него backend не стартует. Генерация:
`openssl rand -base64 48`. Смена секрета инвалидирует все активные сессии.

## Публикация контента

Предмет, раздел и тема бывают **черновиком** или **опубликованы** — за это
отвечает `published_at`. Новый контент создаётся черновиком: тему можно завести,
наполнить материалами и вопросами и только потом открыть ученикам.

Видимость наследуется по цепочке предмет → раздел → тема: снять с публикации
предмет достаточно, чтобы спрятать всё внутри. Условие собрано в
`backend/src/visibility.js` — в кабинете ученика оно нужно в шести запросах,
и забытое звено в одном из них показало бы неготовый материал.

Принятые решения:

- **Отметка времени, а не булев флаг**: «когда тему открыли» спрашивает
  аналитика, а `NULL` естественно читается как «ещё не открыта».
- **Черновик для ученика — 404, а не 403**: отказ выдал бы сам факт, что такой
  предмет готовится.
- **В новые планы попадают только опубликованные темы**, а по неопубликованному
  предмету план не создаётся вовсе (400): он вышел бы пустым и молча.
- **Скрытая тема не запирает следующую** — она выпадает из цепочки
  последовательного прохождения, иначе ученик застрял бы за пунктом, которого
  не видит.

## Доступ к темам внутри плана

Публикация прячет тему у всех. Доступ в плане — у конкретного ученика, и это
три независимых механизма поверх порядка тем:

| Что               | Где живёт                            | Что делает                                 |
| ----------------- | ------------------------------------ | ------------------------------------------ |
| Строгий порядок   | `learning_plans.sequential`          | нужен ли гейт «сначала закрой предыдущую»  |
| Ручное открытие   | `learning_plan_items.unlocked_at`    | тема доступна в обход гейта и расписания   |
| Дата открытия     | `learning_plan_items.available_from` | тема откроется не раньше этого дня         |
| Скрытие у ученика | `learning_plan_items.hidden_at`      | тема убрана у одного, остальных не трогает |

Приоритет проверяется в одном месте (`topicAccess` в `backend/src/me.js`):
скрытие → ручное открытие → расписание → гейт. Ручное открытие сильнее
расписания: если учитель разрешил, дата не отменяет разрешение.

Причина закрытия доезжает до кабинета — ученик видит «Откроется 05.09.2026», а
не общий замок. Скрытая тема отвечает 404: для ученика её не существует.

## Геймификация и её настройки

Опыт, уровни, серия и значки в кабинете ученика **выводятся** из освоенных тем
и попыток тестов — отдельных счётчиков в БД нет и заводить их не нужно: они
разошлись бы с реальным прогрессом.

Настраиваются при этом **правила**, а не результаты: на вкладке «Настройки»
администратор меняет XP за тему, шкалу уровней с титулами, порог зачёта теста и
условия значков, после чего величины пересчитываются из тех же данных. Ручного
начисления XP нет намеренно.

Правила лежат в `app_settings` как «ключ → JSON». Пока записи нет, действуют
значения по умолчанию из `backend/src/gamification.js` — поэтому дефолты описаны
ровно в одном месте, а «сбросить» удаляет строку, а не записывает их копию.

## Аналитика

Раздел «Аналитика» в админке (право `users:read`):

- **сводка** за неделю/месяц/квартал/год — учеников, из них занимались,
  попытки, средний прогресс;
- **срез по ученикам** с фильтрами по классу, экзамену и предмету;
- **карточка ученика** — планы, история попыток и темы, где он застрял
  (попытки были, зачёта нет);
- **аналитика контента** — доля зачётов по теме, средний балл, сколько попыток
  нужно до зачёта, сколько учеников встали;
- **выгрузка CSV** с учётом фильтров (разделитель `;` и BOM — иначе русский
  Excel открывает файл одной колонкой и в кракозябрах).

Своих таблиц у аналитики нет: всё считается из попыток и статусов тем. Прогресс
и попытки собираются отдельными подзапросами — join их напрямую размножил бы
строки и завысил обе цифры у ученика с несколькими планами.

## Миграции

Схема БД описана SQL-файлами в `backend/migrations/`, они применяются по порядку
имён при старте backend и каждый ровно один раз — применённые записаны в таблице
`schema_migrations`. Раннер — `backend/src/migrate.js`; он берёт advisory lock,
поэтому при нескольких экземплярах backend миграции применит только один.

Взят простой раннер на чистом SQL, а не библиотека миграций: видно, что именно
уйдёт в базу, и не нужно осваивать отдельный формат описания. Обратных миграций
нет намеренно — откат делается новым файлом.

```bash
docker compose exec backend npm run migrate   # применить вручную
```

Правила работы с миграциями в командной разработке — в
[CONTRIBUTING.md](CONTRIBUTING.md#изменения-схемы-бд).

## Структура

- `backend/` — Express API, health-check `/api/health`, подключение к Postgres через `pg`
  - `roles.js` — источник правды по ролям и правам
  - `catalog.js`, `plans.js`, `students.js` — контент, планы и ученики (персонал)
  - `me.js` — кабинет ученика: доступ по принадлежности данных
  - `visibility.js` — общее правило видимости опубликованного контента
  - `gamification.js`, `settings.js` — правила опыта/уровней/значков и их настройка
  - `analytics.js` — срезы по ученикам и контенту, выгрузка CSV
  - `backend/migrations/` — SQL-миграции схемы
  - `backend/test/` — тесты на встроенном `node:test`, идут против настоящего Postgres
- `frontend/` — Vue 3 + Vite + Vuetify, форма входа, кабинет ученика и админка
- `docker-compose.yml` — postgres + backend + frontend (nginx, отдаёт статику и проксирует `/api` на backend)
- `.github/workflows/` — проверки на pull request (`ci.yml`) и автодеплой (`deploy.yml`)
- в корне — ESLint, Prettier и `.editorconfig`, общие для backend и frontend

## Проверки

```bash
npm ci && npm run lint && npm run format:check   # в корне репозитория
docker compose exec backend npm test             # тесты backend
```

Тесты идут против **той же локальной базы**, что и приложение: они чистят
таблицы и пересоздают схему. Данные, которыми вы игрались руками (включая
администратора из `create-admin.js`), после прогона исчезнут — это нормально
для локальной разработки, но не запускайте их против базы, которую жалко.

Те же три проверки — линтер, тесты и сборка образов — выполняются на каждый
pull request (`.github/workflows/ci.yml`).

## Деплой

Проект развёрнут на VPS и открыт по адресу https://smartalise.ru.

Как это устроено:

- **Контейнеры не публикуют портов на хост.** Postgres и backend доступны только
  внутри сети compose-проекта, снаружи открыт лишь frontend — и то через
  реверс-прокси.
- **Наружу смотрит общий Caddy**, который занимает 80 и 443 и терминирует HTTPS.
  Frontend подключён к его сети с алиасом `happy-edu-frontend`, на который Caddy
  и проксирует домен. Сертификат Let's Encrypt выпускается и продлевается
  автоматически.
- **Отдельный compose-проект** `happy-edu`: на том же сервере работают другие
  приложения, и они не должны задевать друг друга.

Конкретный адрес сервера, пользователь и SSH-ключ хранятся в секретах
репозитория и в конфигурации деплоя — в коде и документации их нет.

### Команды на сервере

Из директории проекта:

```bash
docker compose -f docker-compose.prod.yml -p happy-edu ps
docker compose -f docker-compose.prod.yml -p happy-edu logs -f
docker compose -f docker-compose.prod.yml -p happy-edu up -d --build   # передеплой вручную
```

### Автодеплой (GitHub Actions)

Изменения, попавшие в `main`, автоматически выкатываются на https://smartalise.ru —
`.github/workflows/deploy.yml`. Деплой запускается **не по самому push**, а после
успешного завершения workflow «Проверки» на этом коммите: код с красными тестами
на сервер не уезжает. Деплоится именно проверенный коммит (`workflow_run.head_sha`),
а не текущая вершина ветки.

Запустить вручную можно из вкладки Actions («Run workflow») — тогда проверки
не учитываются.

Что делает workflow:

1. проверяет, что на сервере есть `/opt/happy-edu/.env` и хватает места на диске
   (меньше 700 МБ — деплой останавливается, не начав ломать рабочую версию);
2. переносит код через `rsync` (без `.env`, `node_modules`, `dist`, `.git`);
3. помечает текущие образы тегом `:previous` — это точка отката;
4. пересобирает и поднимает контейнеры с `--force-recreate`;
5. **проверяет результат**, а не код возврата: сверяет ID собранного образа с тем,
   на котором реально работает контейнер, и опрашивает `https://smartalise.ru/api/health`
   до 10 раз. Если что-то не так — шаг падает и печатает логи контейнеров.

Одновременные деплои исключены (`concurrency`), иначе два `rsync` перетёрли бы
файлы друг друга.

Секреты репозитория (Settings → Secrets → Actions):

| Секрет                 | Назначение                                                      |
| ---------------------- | --------------------------------------------------------------- |
| `VPS_SSH_KEY`          | приватный ключ деплоя (пара к `~/.ssh/id_ed25519_happy_edu_ci`) |
| `VPS_KNOWN_HOSTS`      | host-ключи сервера, чтобы не отключать проверку хоста           |
| `VPS_HOST`, `VPS_USER` | адрес сервера и пользователь                                    |

Ключ деплоя — **отдельный** от личного: его можно отозвать, удалив
соответствующую строку из `authorized_keys` на сервере, не трогая свой доступ.

**Откат** (автоматического нет — деплой только сообщает о провале). На сервере,
в директории проекта:

```bash
docker tag happy-edu-backend:previous happy-edu-backend
docker tag happy-edu-frontend:previous happy-edu-frontend
docker compose -f docker-compose.prod.yml -p happy-edu up -d --force-recreate
```

Откат возвращает код, но **не откатывает схему БД**: миграции только добавляют
объекты, поэтому старый код с новой схемой обычно работает. При изменениях,
которые удаляют или переименовывают что-то в схеме, это перестанет быть верным —
такие миграции стоит разбивать на шаги, совместимые с предыдущей версией кода.
