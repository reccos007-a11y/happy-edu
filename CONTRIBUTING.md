# Как участвовать в разработке

## Что нужно на машине

Только **Docker** и **git**. Node.js локально не обязателен — все команды
выполняются в контейнерах. Если Node всё же установлен, команды можно запускать
и напрямую.

## Первый запуск

```bash
git clone https://github.com/reccos007-a11y/happy-edu.git
cd happy-edu
cp .env.example .env      # значения для локальной разработки менять не нужно
docker compose up --build
```

- Сайт: http://localhost:8080
- API: http://localhost:3000/api/health

Первый запуск применит миграции и создаст пустую базу. Чтобы попасть
в админ-панель, заведите администратора:

```bash
docker compose exec backend node src/create-admin.js admin@example.com
```

Пароль будет напечатан один раз.

## Ветки и pull request

`main` — то, что работает на https://smartalise.ru. **Прямо в `main` не пушим**,
даже если очень надо: каждый push в `main` автоматически уезжает на боевой сайт.

```bash
git checkout -b feat/короткое-описание
# ...правки...
git push -u origin feat/короткое-описание
```

Дальше — pull request. Слить его может автор после того, как проверки позеленели
и кто-то посмотрел код.

Префиксы веток: `feat/` — новая функциональность, `fix/` — исправление,
`chore/` — инфраструктура и рутина, `docs/` — документация.

## Проверки

На каждый pull request запускаются три job'а — те же команды можно выполнить
у себя до пуша:

```bash
# линтер и форматирование (в корне репозитория)
docker run --rm -v "$PWD":/app -w /app node:20-alpine sh -c 'npm ci && npm run lint && npm run format:check'

# отформатировать всё разом
docker run --rm -v "$PWD":/app -w /app node:20-alpine sh -c 'npm ci && npm run format'

# тесты backend (нужна поднятая база из docker compose)
docker compose exec backend npm test
```

Тесты идут против настоящего Postgres: часть гарантий (например, что нельзя
снять роль с последнего администратора при одновременных запросах) на заглушках
не проверяется.

## Изменения схемы БД

Схема живёт в `backend/migrations/*.sql` и применяется автоматически при старте
backend. Каждая миграция выполняется один раз — применённые записаны в таблице
`schema_migrations`.

Чтобы изменить схему, добавьте **новый** файл со следующим номером:

```
backend/migrations/003_короткое_описание.sql
```

Правила:

- **уже влитую миграцию не редактируют.** У тех, кто её применил, база не
  изменится — правка просто не выполнится, и схемы разойдутся;
- пишите так, чтобы миграция прошла на базе, где часть изменений уже есть
  (`IF NOT EXISTS`, `DROP ... IF EXISTS`): на сервере база живая, с данными;
- если добавляете роль — её нужно внести и в `backend/src/roles.js`, и в новую
  миграцию: список ролей закреплён CHECK-ограничением.

Применить миграции вручную:

```bash
docker compose exec backend npm run migrate
```

## Как код попадает на сайт

Слияние в `main` → workflow «Проверки» → при успехе автоматически запускается
«Деплой на VPS» → https://smartalise.ru. С красными проверками деплой не идёт.

Подробности деплоя, отката и устройства сервера — в [README](README.md).

## Секреты

`.env` не хранится в репозитории и не переносится на сервер деплоем. Боевые
значения лежат только в `/opt/happy-edu/.env` на сервере. Если нужно поменять
`JWT_SECRET` — учтите, что все активные сессии станут недействительными.

Ключи, пароли и токены не коммитим никогда, даже во временные ветки: удалить
их из истории репозитория гораздо сложнее, чем не добавлять.
